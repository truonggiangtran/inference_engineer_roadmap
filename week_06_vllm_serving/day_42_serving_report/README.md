# Day 42: vLLM Serving Report

**Time:** 45 minutes. **Goal:** Explain one serving study reproducibly.

## Knowledge

A useful serving report connects user-visible measurements to workload and runtime
configuration. It must make clear whether throughput means requests per second,
output tokens per second, or a model-forward rate. Client-visible first-content
latency is not the same as GPU prefill duration, and a chunk-gap series is not
automatically per-token latency.

Reproduction requires exact revisions, dependency versions, hardware, commands,
request settings, cache state, and raw samples. A chart without those boundaries
cannot establish a fair comparison. A small model and one GPU make a manageable
study, but restrict conclusions about other architectures, context sizes, and
multi-GPU deployments.

Explain at least one tradeoff and one unresolved question. An improved aggregate
throughput with worse first-output latency may be useful for one application and
unacceptable for another. Avoid selecting a universal winner from one metric.
Prepare the same workload and measurement contract for SGLang so that next week's
comparison tests runtime behavior rather than changes in prompts or client code.
Keep actual measurements blank until generated by your server runs.
